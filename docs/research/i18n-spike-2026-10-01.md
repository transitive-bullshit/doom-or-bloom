# i18n spike: Doom or Bloom (2026-10-01)

Read-only research. No repo files changed, no paid calls, no servers. Versions checked on npm on 2026-10-01; Next.js facts from the installed `node_modules/next` 16.3.5 docs.

Status: phases 1 and 2 are implemented with the owner's decisions (en and es; no proxy; no suggestion banner; short `/pt` and `/zh` URL segments with `pt-BR` and `zh-Hans` tags; authored content left to phase 3). [INTERNATIONALIZATION.md](../INTERNATIONALIZATION.md) is the current contract.

## Recommendation

1. **UI copy: next-intl 4.x** (4.14.8, released 2026-09-29; peer deps `next ^16`, `react ^19`). **Authored assessment content** (questions, recovery copy, level/claim text, findings, resources, P(doom) bands) goes elsewhere: it becomes versioned per-locale overlays loaded by the existing content loader, not UI message keys.
2. **Routing: locale-prefixed URLs, English unprefixed** (`localePrefix: 'as-needed'`). Every existing URL and shared link stays valid, and each language gets its own static, CDN-cacheable page with hreflang. Only an explicit choice redirects: a `NEXT_LOCALE` cookie, set by the selector. Accept-Language never redirects; it only drives a client-side "View in Español?" suggestion.
3. **localStorage alone won't work here.** Static pages (`dynamic = 'error'` on `/`, `/about`, `/users`, sitemap, llms.txt) can't read it at render time. Crawlers would only ever see English. Users would get an English flash on every load. Use the URL as the source of truth, the cookie for explicit choice, and localStorage only for UI conveniences such as a dismissed banner.
4. **Jev stays English.** The engine already requires stored prompt text to equal the English authored text (`validateSnapshot`, `lib/server/engine.ts:143–155, 215`), so translate only the display layer. Snapshots keep canonical English. Record the display locale per answer. Before launching the interview in hi/th/zh/ja, run the bounded paired validation below: TypeSafe's own docs say English is where Jev is most accurate.
5. **Simulated users (144):** in phase 1, keep answers in English with a note, and localize the chrome and authored result copy. Mark non-English variants `noindex` with the English page as canonical, because Google warns against pages where only the boilerplate is translated. Translating answers at publish time can come later and then earns hreflang indexing.
6. **Locales:** en (default), es, pt-BR, hi, zh-Hans, th, ja, de. Suggested additions: fr, ko, id. Arabic/Hebrew would need RTL work (see open decisions).

## 1. Library choice

| --- | --- | --- | --- | --- | --- |
| RSC + static generation | Native. `next/root-params` (new in 16.3) gives any Server Component the locale without prop drilling. `generateStaticParams` in the `[locale]` root layout | First-class: `getTranslations` in RSC, `useTranslations` in client and non-async server components. Static rendering requires the locale from params (`setRequestLocale`/`hasLocale`) | RSC supported, but needs per-page `setI18n` setup plus macros compiled by an SWC plugin pinned to Next's SWC version. Fragile across Next upgrades (this repo builds with `--webpack`) | Compiler emits one function per message. | Client bundle | You choose what to pass to client components | Small runtime plus ICU parsing. Client messages are whatever you give `NextIntlClientProvider`, which should be scoped per surface | Compiled catalogs, small | Smallest: messages tree-shake per function | Largest runtime of the set |

| Fit with committed JSON in Git | Good | Good (`messages/<locale>.json`) | Good (PO) | Good (inlang JSON) | Fine |

**Why next-intl.** Most of the copy lives in 62 client components (~230 strings in `components/assessment/` alone). Those need a provider, ICU plurals ("Question {n} of {limit}"), rich text, and locale-aware `Link`/`redirect`/`usePathname`. The dictionary pattern plus root params covers only the server half, so you'd end up rebuilding next-intl. Lingui's macro/SWC coupling is a maintenance risk on a fast-moving Next. Paraglide only wins on bundle size, which isn't a constraint here, and it costs ICU plus a hand-built Next integration. react-i18next is the older client-first approach.

**Unverified here:** exact bundle kB and the status of next-intl's `useExtracted`, precompilation, and `root-params` adoption. The web-research subtask had not returned when this was written; check the next-intl changelog before phase 1.

## 2. Routing and persistence

**Choice: `app/[locale]/…` + `as-needed` + no Accept-Language redirects.**

- **Google's guidance:**
  - Use "different URLs for each language version… rather than using cookies or browser settings" ([managing multi-regional sites](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites)).
  - Googlebot "sends HTTP requests without setting `Accept-Language`" from US IPs ([locale-adaptive pages](https://developers.google.com/search/docs/specialty/international/locale-adaptive-pages)).
  - "Avoid automatically redirecting users from one language version… to a different language version."
- **Static and CDN.** PERSISTENCE.md notes that Vercel keys cached responses by path, not cookies. Locale-in-path keeps every page `force-static`/ISR with 48h revalidate. Budget build time: roughly 9× the static pages.
- **Metadata.** Wire `metadata.alternates.languages` (hreflang plus `x-default` → English) through `lib/metadata.ts`, which today hard-codes `openGraph.locale: 'en_US'`. Add sitemap `alternates.languages` per URL; Next supports both natively.
- **llms.txt.** Keep one English `/llms.txt` and add a "Languages" section listing `/es`, `/pt`, and so on.
- **Proxy.** Add a Next 16 `proxy.ts` (middleware is deprecated in 16) with a narrow matcher that excludes `api`, `_next`, images, OG routes and `/public/assessments/*/data`. It does three things:
  - rewrites unprefixed paths to `en` internally;
  - redirects unprefixed requests to the cookie locale when `NEXT_LOCALE` is set;
  - otherwise passes the request through.

  If proxy invocation cost matters, `next.config` `rewrites` plus `redirects` with `has: [{type:'cookie'}]` achieve the same without a function. Test that on a preview deployment.

- **Detection.** Only on the client: compare `navigator.languages` with supported locales and show a dismissible banner. Remember the dismissal in localStorage.
- **Persistence.** Use the `NEXT_LOCALE` cookie: 1 year, `SameSite=Lax`, set only on explicit selection, so it's a strictly functional preference cookie. The URL stays authoritative.
- **Selector.** Put it in the footer, which already holds About/Privacy/methodology; the header already carries the CTA, social links, theme and account. Use a shadcn Select of endonyms (Español, Português, हिन्दी, 中文, ไทย, 日本語, Deutsch) that keeps the current path.
- **Path-prefix consumers to update:**
  - `robots.ts` disallow rules;
  - Vercel Analytics path filters and PostHog paths (add a `locale` property);
  - `site-breadcrumbs.tsx` `pageLabels`;
  - `outputFileTracingIncludes` globs and `revalidatePath` calls. Publication must expire all locale variants of a public assessment.
- **Keep outside `[locale]`:** `api/`, `admin/`, dev-only `/questions`, `/corpus`, `/user-journeys`, `/prototypes`.

## 4. Content pipeline and committed translations

**Today:**

- `content/manifest.json` points at `content/releases/<contentVersion>/` (prompts, findings, resources, references, provenance) and `content/rubrics/<rubricVersion>/`.
- `loadBundle(version)` validates the graph and version pins.
- `content:freeze <reviewer> <changelog>` writes SHA-256 hashes of every release and rubric file into the release and root manifests. It refuses unless required-source review is complete.
- `content:assemble` builds drafts with `provenance.json`. `test:content` validates bundles and intake.
- Saved assessments pin content, rubric and assessment versions.

**Proposal (additive; English files unchanged):**

```
content/releases/0.4.0-draft/l10n/<locale>.json   # prompts{id:{text,reask,clarification,exhausted}}, findings{id}, resources{id:{title,purpose,question,effort}}
content/rubrics/0.1.0-draft/l10n/<locale>.json    # dimensions{id:{label,levels[]}}, catastrophicRisk
content/l10n/code/<schema-version>/<locale>.json   # facets, doomBands, worldview-experiment labels, placement questions, unplaced scopes (keyed by the code's version constants)
messages/<locale>.json                             # next-intl UI chrome
content/l10n/meta/<locale>.json                    # per-entry: sourceHash (sha256 of English), model, translatedAt, reviewStatus, reviewer
```

- **Pinning.** Each l10n file sits inside the release directory, so `bundleFiles()` hashes it and `content:freeze` covers it. A frozen release freezes its translations too. A translation fix after freezing means a new content version, or an explicit `l10nRevision` recorded in `meta` if you want to fix a typo without re-versioning. Decide which.
- **Validation** (extend `scripts/validate-content.ts`, run under `test:content`). For every supported locale and every supported content version:
  - every English ID has an entry;
  - no extra IDs;
  - `sourceHash` matches the current English text, so a stale translation fails;
  - ICU placeholders match;
  - for `levels[]`, array lengths match.

  A missing locale for an old version falls back to English per entry with a visible "original language" note. The build never fails on old versions.

- **Translation script.** `pnpm l10n:translate --locale=hi [--only-stale]`:
  - diffs `sourceHash`, sends only new or changed entries to an LLM with a glossary (Doom, Bloom and P(doom) stay untranslated; the locked subtitle and root prompt get reviewed wording) and a style note (neutral, plain register, no loaded premises);
  - writes JSON and meta with `reviewStatus: 'machine'`;
  - requires `--allow-paid`, following house rules.

  Then `pnpm l10n:review --locale=hi` emits a side-by-side review packet in the style of the repo's `*-review-packet.md` for a native-speaker pass, setting `reviewed`. `content:freeze` could require `reviewed` for the root prompt, the 4 recovery strings and the claim levels.

- **Old saved assessments.** Render by `(pinnedContentVersion, locale)`. If that version's l10n exists, prompts, claims, findings and resources localize via IDs, and participant answers stay as written. If not, fall back to stored English with a note. Released versions 0.1–0.3 need back-filled l10n only if you want old results localized. Otherwise the fallback is acceptable.

## 5. Engine risk (Jev)

**What Jev receives:**

- `current: {prompt: p.text, answer}` (`engine.ts:1160`);
- `usableHistory` / `completeParticipantEvidence` (prompt text plus raw answers);
- rubric `dimensionDefinitions` (label plus meaning);
- authored instructions and criteria from `content/rubrics/*/questions.json`;
- level texts as Choice options;
- routing candidates' text and targets;
- facet, P(doom) band and worldview-experiment options from code.

Jev writes no prose. Participant-visible text comes from authored content, participant answers (and stated P(doom) tokens taken from them), and code templates. So the only non-authored display text is the participant's own words.

**Risks:**

1. **Accuracy.** TypeSafe: "English is the primary training language and where accuracy is currently best. Other languages, including CJK scripts, are handled but not equally well; test on your own content… pay close attention to Confidence" ([docs.typesafe.ai/models](https://docs.typesafe.ai/models)). Expect more `disposition` rejections (triggering recovery loops) and lower confidence, which widens ranges and delays readiness.
2. **Tokens.** Devanagari and Thai tokenize at several times English. See [Petrov et al. 2023](https://arxiv.org/abs/2305.15425) for the general effect; not measured for Jev's tokenizer. Jev bills input tokens ($0.042/M) and has a 64k context. The 20,000-character answer cap can overflow context in Hindi or Thai, where it can't in English. Consider a per-script cap.
3. **Stated P(doom) extraction is English-only** (`worldview-experiment.ts:134`, `pdoom.ts:128`):
   - `\d` misses Devanagari (३०), Thai (๓๐) and full-width (３０) digits, and full-width `％`;
   - "percent" words (por ciento, Prozent, パーセント, 百分之三十) aren't recognized;
   - English-only qualifiers ("less than") mean "menos de 5%" loses its bound;
   - the sentence split ignores `。！？।`.

   This is the same silent-drop class as the 0.7.2 bug. The fix: normalize digits with NFKC plus a digit map, and add localized qualifier tables.

4. **Exact English commands.** `local-reply.ts` recognizes only `test`/`paperclips`. That's harmless, but the commands are English-only.

**Design.**

- Keep all Jev inputs canonical English, including the prompt text: look it up by `promptId` in the English bundle, which the stored snapshot already holds.
- Pass answers verbatim. Don't machine-translate answers, which would add an unaudited model in the loop.
- Add `answer.displayLocale` (and optionally the snapshot's l10n hash) so the exact displayed question can be reconstructed from Git.
- Optionally add one neutral line to the evidence policy: "Answers may be in any language; judge meaning, not fluency." That's a rubric change, so version it.

**Bounded validation plan (not run):**

- **(a) Offline, no cost.** Unit tests for the P(doom) candidate extractor with multilingual fixtures.
- **(b) Paired invariance probe.** Take ~12 existing benchmark answers covering doom, bloom, mixed and skeptical views, short and detailed. Machine-translate them, then have a native speaker spot-check, into hi, th, zh, ja, plus es as a control. Run interpret plus projection only, English versus translated. Measure:
  - disposition acceptance;
  - |Δx| and |Δy|;
  - P(doom) band agreement;
  - mean confidence.

  That's about 60 paired runs under the existing `--allow-paid --max-requests` caps, and dollar cost is trivial at Jev prices.

- **(c) Benchmark arm.** If (b) passes, add a `language` dimension to `benchmark:run` with the `retest` set in `brief` style for two languages. Use `compare` bootstrap CIs.
- **Gate.** Mean |Δx|, |Δy| ≤ 0.05, the documented retest noise, and no disposition-rejection increase above one per interview. A locale that fails ships its UI but shows an "answers in English work best" note in the interview.

## 6. Simulated-user pages

The answers are LLM-generated English stored in Postgres (`assessment_snapshots.payload`), not in Git. The authored parts of each result (claims, findings, map labels) localize automatically via §4.

| Option | UX | SEO | Cost |
| --- | --- | --- | --- |
| A. English only, `/users/*` unprefixed | Worst for non-English visitors | No duplicates | None |
| **B. Localized chrome and results, English answers with a note (phase 1)** | Good | Non-English variants `noindex` + canonical to English; left out of sitemap alternates. Google: translating only boilerplate "can create a bad user experience if the same content appears multiple times in search results" | Build ~144×8 more pages, or render them on demand (`dynamicParams`) and pregenerate English only |
| C. Translate answers at publish time | Best | Full hreflang: 144×8 genuinely localized pages about well-known thought leaders' views, the largest SEO upside | About 1–2M words across 8 locales: tens of dollars in model cost, spot review only. Store translations in a committed artifact keyed by simulation ID + answer hash (e.g. `content/l10n/personas/<locale>/<simulationId>.json`), or a DB table if you'd rather keep persona data out of Git. Regenerating a persona invalidates its translation |

Recommend B now and C once the benchmark shows the English pipeline is stable. Apply the same policy to `/public/assessments/<id>`: localized chrome, answers as written, non-English variants `noindex`.

## 7. Fonts

- **UI.** The system stack (`Arial, Helvetica, sans-serif`) already falls back to OS fonts for Devanagari, Thai and CJK on every major OS. Keep it; web-font CJK is multi-MB.
- **Per-script stacks.** Add them via `:lang()`:
  - `:lang(hi)`: `'Nirmala UI', 'Kohinoor Devanagari', 'Noto Sans Devanagari'`;
  - `:lang(th)`: `'Leelawadee UI', Thonburi, 'Noto Sans Thai'`;
  - `:lang(zh)`: `'PingFang SC', 'Microsoft YaHei', 'Noto Sans SC'`;
  - `:lang(ja)`: `'Hiragino Sans', 'Yu Gothic', 'Noto Sans JP'`.
- **Layout.** Set `<html lang>` per locale, because it picks the right Han glyphs for zh versus ja. Relax the negative Latin `letter-spacing` and the tight `line-height` for these scripts. Thai and Devanagari have tall stacked marks. Thai has no word spaces, so rely on the browser's line breaking and avoid `word-break: break-all`.
- **Takumi share and OG images.** No system fonts are available at render time, so non-Latin text renders as tofu. Register subset fonts: Noto Sans Devanagari, Noto Sans Thai, and Noto Sans SC/JP subset to the glyphs in the committed catalogs. Commit the woff2 files under `lib/sharing/fonts/` (OFL), use Takumi's `fontFamilies` fallback chain, and set the per-render `lang` option (`@takumi-rs/core` types). Include the fonts in `outputFileTracingIncludes`.
- **Card text.** Keep persona names Latin. Localize the axis labels, "My AI Worldview" and similar. Replace `Intl.DateTimeFormat('en-US')` in `render-card.tsx` with the locale. Version the image URL by locale (`?v=…&l=es` or `/es/…/opengraph-image`).
- **Site OG image.** Generate one committed `opengraph-image.png` per locale via `social-image:generate --locale`.

## Architecture sketch

```
app/
  [locale]/layout.tsx          # root layout: <html lang>, NextIntlClientProvider (scoped messages), generateStaticParams(locales)
  [locale]/page.tsx, about/, privacy/, users/, users/[username]/, public/assessments/[id]/, assessments/, assessment/
  [locale]/sitemap.ts? -> keep app/sitemap.ts at root emitting alternates
  api/, admin/, questions/, corpus/, llms.txt/   # outside [locale]; separate root layout for admin/dev
proxy.ts                       # next-intl createMiddleware(routing) + cookie-only redirect, narrow matcher
i18n/routing.ts                # defineRouting({ locales, defaultLocale:'en', localePrefix:'as-needed', localeDetection:false })
i18n/request.ts                # getRequestConfig: messages/<locale>.json
messages/<locale>.json
lib/content/l10n.ts            # localizeBundle(bundle, locale), localizeClaim(component, locale), localizePrompt(instance, locale)
```

- **Server Components:** `const t = await getTranslations('Results')`. Pages call `setRequestLocale(locale)`, or read the locale from root params, so rendering stays static.
- **Client components:** `useTranslations('Interview')`. The provider gets only the namespaces that surface needs.
- **Authored content** doesn't go through `t()`. The server page calls `loadBundle(version)` → `localizeBundle(bundle, locale)` and passes a small `{prompts, levels, findings, resources}` catalog as props, as `app/assessments/[id]/page.tsx` already does for `dimensions`.
- **Interview API responses** stay canonical. The client resolves display text by ID from that catalog. For `presentResult`, add a locale-aware `presentResultText` step.

## Risks

- **Stored English is validated by exact match.** A translated string written into a snapshot would break `validateSnapshot` and `isAuthoredClaim`. The rule: never store display text.
- **Jev accuracy and tokens outside English.** Could silently worsen placements for hi/th/zh/ja participants. Gate with the §5 probe.
- **Translation drift and neutrality.** Loaded wording in a translated question invalidates cross-language comparison. The root prompt, recovery copy and claim levels need native review. Treat results in different languages as not yet comparable in MEASUREMENT.md.
- **Build size and time.** Roughly 9× the static pages if everything is pregenerated. Mitigate with on-demand non-English persona pages.
- **Cache invalidation.** Publication must expire every locale variant of a public page and image.
- **Proxy.** Adds a function hop on every page request (cost and latency) where there's none today. The `next.config` alternative exists.

## Open decisions for Travis

1. **Region codes.** `pt-BR` versus `pt`, and `zh-Hans` only, or add `zh-Hant` (Taiwan/HK)?
2. **Extra locales.** Add fr, ko, id; skip ar/he for now? RTL costs a `dir` attribute, logical Tailwind classes (`ms-`/`me-`) throughout, and mirrored map and axis semantics, where Doom/Bloom left-right would need an explicit decision.
3. **Interview gating.** Enable the interview in locales that fail the Jev probe with an "English works best" note, or UI-only?
4. **Persona answers.** Option B now, C later, or C now?
5. **Translation fixes after freeze.** Require a new content version, or allow an `l10nRevision`?
6. **Review bar.** Is a native-speaker review required before a locale goes live, or only for the root prompt and claim levels?
7. **Answer-language hint.** Add the one-line "any language" note to the Jev evidence policy? It's a versioned rubric change.

## Addendum: verified web research (arrived after the report)

The web-research check confirms next-intl 4.14.8 as the fit and changes these details:

- **Static rendering.** Use `next/root-params` (on by default in Next 16.3) inside `i18n/request.ts`, via `await rootParams.locale()` then `hasLocale`. `setRequestLocale` is now legacy. Root params aren't available in Route Handlers, Server Actions or `unstable_cache`, so pass the locale explicitly there. `force-static` empties `headers()`/`cookies()`, so never look up the locale from headers.
- **Cookie.** next-intl's `NEXT_LOCALE` defaults to a session cookie with no max-age. Give it a max-age through `localeCookie` so an explicit choice persists. Set `localeDetection: false`: no Accept-Language redirects, only the client-side suggestion banner.
- **Vercel caching.** Since 2026-09-30, responses with `set-cookie` or `Vary: Cookie` are not cached. Set the cookie on the client when the user picks a language, never in proxy or page responses.
- **Proxy cost.** Proxy runs before the cache: one Fluid invocation per request, and cached static pages are still served. The `next.config` `redirects` with `has: [{ type: 'cookie' }]` alternative avoids the function.
- **Client bundle.** By default in v4, `NextIntlClientProvider` sends all messages. Pass only the namespaces each surface needs. Consider `experimental.messages.precompile`, which brings the client to about 4 kB gzip.
- **Takumi.** It never reads system fonts. Its `googleFonts()` helper fetches only the subsets it needs, but committed subset files keep renders deterministic and offline. The `lang` option drives Han glyph selection and line breaking.
- **Locale additions.** Measured by web content share and users, the strongest additions are fr, id and ru, then ko, tr and vi. Arabic needs RTL work: shadcn's RTL mode has shipped, with manual fixes still needed for some components. **Suggest fr + id** rather than fr + ko.
- **Unverified:** Takumi's Thai line breaking and Devanagari shaping beyond its dependency list. Test these in phase 5.
